# Issue Selection Rubric

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Maintainer active | Repo-facts block: archived status, last 5 default-branch commit dates, latest release date, and maintainer first-response sample. | Pass if the repository is not archived and has at least one default-branch commit or release within the last 90 days, OR there is evidence of a maintainer response within the last 30 days. Fail if the repository is archived or the available activity evidence shows no maintainer or development activity within the last 90 days. | required |
| Repo in use | Repo-facts block: archived status, last push date, latest release date, last 5 default-branch commit dates, and open issues/PR count. | Pass if the repository is not archived and has a push, release, or default-branch commit within the last 90 days. Fail if archived or if there is no qualifying activity within 90 days. | required |
| Scope fits | Issue title and body, labels, author role, linked PR status, and issue comment thread. Use the locations described in references/evidence-guide.md when additional scope evidence is provided. | Pass when the issue identifies one coherent outcome or concrete bug and provides enough information or maintainer-curated scope signals for a contributor to begin investigating or implementing it. Concrete signals may include specific missing or incorrect behavior, proposed changes, diagnosed causes, expected results, or a maintainer/collaborator-filed issue labeled good first issue. An issue may be concise, touch multiple files, contain several implementation steps, involve performance/concurrency, or require investigation and still pass when those details belong to one coherent outcome. Fail if the issue is an umbrella, megaissue, or tracking list of independent tasks; requires open-ended codebase-wide cleanup; has no usable specification or concrete intended behavior; depends on an unresolved product/design decision; or has a long history showing the apparent scope is misleading, such as prolonged design discussion combined with multiple abandoned or closed implementation attempts without a settled resolution. Do not reject a bounded issue merely because its description is short, its technical domain is unfamiliar, or it may require learning the codebase. A good-first-issue label alone is not sufficient to override clear evidence of unresolved or misleading scope. | required |
| Issue unclaimed | Repo-facts block: current assignees and linked PRs. Issue body and comment thread: current claim or in-progress statements and later evidence that a claim was released, abandoned, completed, or became stale. | Pass if there is no current assignee, no open linked PR, and no evidence that a contributor is currently working on the issue. Historical claims, closed PRs, abandoned attempts, and old expressions of interest do not fail this check when later evidence or the age/context shows they are no longer active. Fail for a current assignee, an open linked PR, or a current explicit in-progress claim. | required |
| Contribution policy allows course workflow | Repo-facts contribution-policy evidence and the relevant contribution-policy location described in references/evidence-guide.md. | Pass if the repository permits contributions made with the course workflow, including policies that allow AI tools subject to human review, testing, or understanding. Fail if the repository explicitly prohibits AI-generated code/documentation or otherwise prohibits the contribution workflow required for this course. If no policy is stated, pass this check. | required |

## Verdict rule

Accept an issue only if every required check passes. Preferred checks, if added later, may rank accepted issues but never change the accept/reject verdict. Treat unclear evidence on any required check as a fail. If the available evidence is insufficient to determine whether a required condition passes, reject the issue.
